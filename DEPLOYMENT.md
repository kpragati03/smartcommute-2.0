# SmartCommute 2.0 — Deployment Guide

Production topology: **Vercel** (React frontend) + **Render** (Django API web
service + managed PostgreSQL). HTTPS is provided by both platforms.

## Live deployment (Nov 2026)

- Frontend: https://smartcommute-2-0.vercel.app
- Backend API: https://smartcommute-backend.onrender.com/api/v1
- Repository: https://github.com/kpragati03/smartcommute-2.0

Demo logins are listed in the README. Note: Render's free web service sleeps
when idle (first request after a pause can take ~30–60 s), and the free
PostgreSQL plan has a limited lifetime — upgrade for a long-lived pilot.

## 1. Backend on Render (Blueprint)

1. Push this repository to GitHub.
2. Render Dashboard → **New → Blueprint** → select the repository.
   Render reads the root `render.yaml` and creates:
   - Web service `smartcommute-backend` (Python, free plan, `rootDir: backend`)
   - PostgreSQL database `smartcommute-db` (free plan)
3. Environment variables are set by the blueprint:
   - `SECRET_KEY` — generated by Render
   - `DEBUG=false`
   - `DATABASE_URL` — wired from the database
   - `ALLOWED_HOSTS=.onrender.com`
   - `CORS_ALLOWED_ORIGINS` / `FRONTEND_URL` — update to the real Vercel URL
     after step 2 (comma-separated origins for CORS)
   - `EMAIL_BACKEND` — console by default; switch to SMTP for real mail
   - `TELEMETRY_THROTTLE_RATE=120/min`
4. Build runs `collectstatic` + `migrate`; start runs gunicorn.
   Note: Render's free web service sleeps when idle (first request after a
   pause takes ~30–60 s), and the free PostgreSQL plan has a limited lifetime
   — upgrade or move to another managed Postgres for a long-lived pilot.

## 2. Frontend on Vercel

1. Vercel → **Add New Project** → import the same GitHub repository.
2. Root Directory: `frontend`. Framework preset: Vite (build `npm run build`,
   output `dist`).
3. Environment variable: `VITE_API_URL=https://<your-render-service>.onrender.com/api/v1`
4. Deploy, then copy the Vercel URL into the Render service's
   `CORS_ALLOWED_ORIGINS` and `FRONTEND_URL` and redeploy the backend.

## 3. Seed + train on production

The trained ETA model (`*.joblib`) is a **generated artifact and is never
committed**. Both seeding and training run **inside the Render build**
(see `buildCommand` in `render.yaml`): every deploy runs
`migrate` → `seed_demo` → `train_eta_model`, so the demo dataset and a
freshly trained model are always present. (Direct database connections
from outside Render may be blocked by some networks/proxies; the build-time
approach avoids needing them.)

Note: `seed_demo` resets the demo dataset on each deploy. For a real pilot,
remove `seed_demo` from the build command and seed once manually instead.

## 4. Verify production

- `GET https://smartcommute-backend.onrender.com/api/v1/` responds (401 without auth is expected).
- Log in on the Vercel frontend with a demo account (see README).
- Run the simulator against production (`api_base_url` in
  `simulator/config.json`) and watch buses move on the live map.
- Check ETA, journey planner, notifications bell, admin analytics.

## 5. Ongoing operations

- Schedule `evaluate_etas` and `detect_anomalies` (cron) to fill actual
  arrival times and raise anomaly incidents.
- Retrain the ETA model periodically on real `LocationHistory` once a pilot
  generates genuine telemetry.
- Back up the PostgreSQL database (Render managed backups / `pg_dump`).
